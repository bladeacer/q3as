# Changelog v0.4.0

Not the whole log: see the [changelog index](index.md) for every version and
the [results index](../results/README.md) for the measured numbers.

No evaluation run was made for this version, so there is no
`result-v0.4.0.md`; nothing here quotes benchmark numbers. What this version
changes is how much host RAM `make train` needs and how long its evaluation
phase takes.

**Read this before comparing losses across versions.** The reported
`eval_loss` and test loss are now measured on a seeded 2,000-example subset of
each split, not the whole split. They are comparable run-to-run within this
version, and not to the full-split figures in
[v0.3.0](v0.3.0.md). The generation metrics (build, test, prove, BLEU,
compliance) are unaffected: nothing in the evaluation path changed.

## Host RAM

`make train` was swapping on a 6 GB host. The cause was the dataset, not the
model. The 423 MB train split was resident three times over: parsed records,
then chat-templated strings, then the Arrow table `Dataset.from_list` built
from them. Measured on the reference host:

| | before | after |
|---|---|---|
| peak anonymous memory | 5,206 MB | 1,444 MB |
| anonymous memory during training | 3,402 MB | 2,024 MB |
| swap used | 223 MB | 0 |

Only anonymous memory is comparable here. `VmRSS` peaks near 5.6 GB during the
model load either way, but that is the safetensors files mapped in and read
once: reclaimable page cache, not memory the kernel has to fight for.

- Each split is now streamed from JSONL into an Arrow table one record at a
  time. One reader ([`iter_usable_records`](../../training/train_unsloth.py))
  feeds the streaming builders and the in-memory fallback, so they cannot
  disagree about which records are trainable or in what order.
- The model load was measured, not assumed: peak anonymous memory during it
  is 1,245 MB. A locally pre-quantized 4-bit checkpoint was built and tried as
  a way to shrink it, and **discarded**: peak was 6,064 MB against the
  bf16 path's 5,661 MB, so it bought nothing and cost a second copy of the
  weights on disk.
- `HF_DEACTIVATE_ASYNC_LOAD=1` stays. Enabling the transformers v5 async
  loader fails on this card with `CUDA_ERROR_OUT_OF_MEMORY` from
  `cuMemSetAccess`.
- Tables are cached under `data/processed/.tokenized/`, keyed on the split's
  content hash, the chat template, the tokenizer's **vocabulary**, the
  truncation length, and a pipeline version. The vocabulary is hashed rather
  than named because a different vocabulary can ship under the same model name,
  and that would train on stale ids. Stale tables are pruned after each run;
  observed 1.3 GB down to 179 MB. `make clean` removes the directory.

## A more efficient format, and pre-tokenizing

The train split is stored as token ids instead of rendered text, which is what
the trainer actually consumes.

| | size of the 65,809-record train table |
|---|---|
| rendered text | 426 MB |
| `input_ids`, int32 | 136 MB |

3.1x smaller, because a token id cannot exceed a 2^31 vocabulary and the
rendered text is mostly Ada source. An `input_ids` column also marks the
dataset as already processed, so trl and Unsloth skip their tokenization pass
entirely: **4m07s per run down to under a second**, verified by the absence of
any `Tokenizing [...]` line in a real run.

This was validated rather than assumed, because Unsloth swaps the data
collator when `input_ids` is pre-supplied. Four steps, same seed, same data:

| step | via `text` | via `input_ids` |
|---|---|---|
| 1 | 2.508410930633545 | 2.508410930633545 |
| 2 | 2.5054378509521484 | 2.5054378509521484 |
| 3 | 2.505420207977295 | 2.5059974193573 |
| 4 | 2.486865282058716 | 2.4875197410583496 |

Steps 1 and 2 are bit-identical, so the ids reaching the model are the same.
Steps 3 and 4 diverge, but a `text` run repeated against itself diverges by
the same magnitude (2.505340814590454 and 2.48789644241333). That is the
bf16 non-determinism the reproducibility caveat in
[`docs/datasets-and-training.md`](../datasets-and-training.md) already
describes, not a difference in the data path.

- The eval splits stay as text, because the chunked eval callback tokenizes
  them itself one example at a time and has no use for a tokenized column.
- They are no longer handed to `SFTTrainer` at all. `eval_strategy` is `"no"`
  and the callback is what measures loss, so passing the split in only made
  trl tokenize 3,709 val records per run to build a dataset nothing read.

## Evaluation time

Evaluation, not training, set the wall time of a run. Measured on the
reference host: 1.2 ms per token for a forward plus the final `lm_head` over
the same tokens, giving 37.1 min for a full val pass (3,709 records, 1,895,645
tokens) and 35.6 min for the test split (3,562 records). A 500-step run at
`--eval-steps 50` is ten evaluations, so **6.8 h of evaluation**.

The GPU is not the constraint and cannot be made the constraint: it reports
95-100% utilization while its SM clock sits at 180 MHz of a 3090 MHz maximum,
drawing 55 W. It is fed small kernels and idles between them. Batching the
eval forwards was measured and rejected: batch 4 is 10% faster (1.040 to
0.940 s per example) and pushes VRAM to 7.18 GB of 8.15 GB. The bitsandbytes
NF4 matmuls are simply slow, so cost is proportional to tokens evaluated.

Three flags now bound it:

- `--eval-sample` (default 2000) draws the subset the during-training
  early-stopping evaluations score. Every evaluation point scores the *same*
  seeded subset in the same order, so the curve compares like with like and the
  early-stopping signal is unchanged in kind; only the sample size differs.
- `--test-sample` (default 2000) does the same for the final held-out metrics.
- `--eval-budget-min` (default 300) is a ceiling, not a control. The run
  projects its evaluation cost up front, logs it, and warns when the chosen
  sample sizes exceed it. It never silently resizes anything.

At the defaults the projection is **3.75 h**, against 6.92 h for the full
splits. `training_summary.json` records `val` alongside `val_total` and
`test` alongside `test_total`, plus the sample sizes and the projection, so a
reported loss cannot be mistaken for a full-split loss.

Training data is untouched: all 65,809 records are still trained on. Only what
the eval callback scores is capped.

## Bugs fixed

- **Every training log line was silently dropped.** Importing unsloth installs
  a root handler and sets the root level to `WARNING`, which makes the
  `logging.basicConfig(level=INFO, ...)` in `main()` a no-op. Split counts,
  eval loss, early-stopping decisions, the summary path, and the warnings were
  all being discarded, and `--verbose` did nothing. The module now configures
  its own logger, which also keeps the third-party INFO firehose out of
  `training.log`.
- A record shaped `{"messages": "not a list"}` passed the `len(messages) >= 2`
  check and then raised `AttributeError` on `.get`, and a non-dict final
  message did the same. Both are now skipped as malformed. Found by a new test,
  not by a run.
- `test_source` reported `fallback-carve` when the test split was simply
  absent and nothing had been carved. It now says `absent`.
- An empty validation file used to fall back to carving val/test out of the
  training data. Streaming cannot carve that late, so the case now warns
  plainly that training is running without eval loss or early stopping instead
  of quietly losing both.
- The startup log said `eval=no` while `--eval-steps 50` was configured. It
  reports the real early-stopping patience.

## Housekeeping

- Removed 8.0 GB of stale `*.incomplete` blobs left in
  `models/qwen3-8b/.cache/huggingface/download/` by interrupted downloads.
  The model itself was verified complete first
  (`download_model.py --check-only`); 23 GB of weights became 16 GB.
- [`gen_agents_tree.py`](../../scripts/gen_agents_tree.py) skips the
  tokenized-cache directory, which would otherwise have put 60-odd cache files
  and lock files into the `AGENTS.md` tree.

## Tests

- New [`tests/test_train_data.py`](../../tests/test_train_data.py), 39 cases:
  the record skip rules, parity between the streaming and in-memory loaders,
  token-id equivalence and truncation, every input to the cache key, the
  determinism and ordering of the eval subsample, the budget projection, and
  the cache prune. unsloth is stubbed, so it costs no GPU and no host RAM.
