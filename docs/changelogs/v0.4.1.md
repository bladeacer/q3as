# Changelog v0.4.1

Not the whole log: see the [changelog index](index.md) for every version and
the [results index](../results/README.md) for the measured numbers.

No evaluation run was made for this version, so there is no
`result-v0.4.1.md`; nothing here quotes benchmark numbers. What this version
changes is what `make train` prints while it evaluates, how many examples
each evaluation point scores, what a run does when it dies half way, what
`make clean` throws away, how a moved upstream commit is noticed, and what
dedup removes.

**Read this before comparing losses across versions.** The per-step
`eval_loss` is now measured on a seeded 256-example subset of the val split
and the reported test loss on a 512-example subset, where
[v0.4.0](v0.4.0.md) used 2,000 examples of each. They are comparable
run-to-run within this version, and not to the 2,000-example figures in
v0.4.0 or the full-split figures in [v0.3.0](v0.3.0.md). The generation
metrics (build, test, prove, BLEU, compliance) are unaffected: nothing in the
evaluation path changed.

**The training set changed too**, from 73,080 to 77,758 turns, and the reason
is in *What dedup was removing* below: the structural cap was cutting defect
turns by the wrong key. Loss figures from a run on the old set and a run on
this one are not comparable for that reason either.

## An evaluation pass no longer looks like a hang

A run reached an evaluation point and printed nothing until the pass
finished. With the v0.4.0 sample size that was 20 minutes of silence between
progress-bar lines, and the only symptom was a bar that had stopped moving at
99/500. The pass now logs as it goes, using the same counter the dataset
stages use ([`Progress`](../../data/processing_scripts/progress.py)), and the
eval-loss line projects the evaluation time still to come from the cost that
pass measured.

A real pass, from `make train` at step 2:

```text
[val eval] starting (256 items)
[val eval] 30/256 (12%) 1.0 items/s, elapsed 31s, eta 3m57s
[val eval] 117/256 (46%) 1.3 items/s, elapsed 1m32s, eta 1m49s
[val eval] 256/256 (100%) 1.6 items/s, elapsed 2m41s, eta 0s
val pass: 256 examples, 143580 tokens, 0.63 s per example
eval_loss at step 2: 2.5663 (best 2.5663); 0.63 s per example, ~0 min of
  evaluation still to come (0 more point(s), then the test pass)
```

## The sample defaults

`--eval-sample` is 256 and `--test-sample` is 512, down from 2,000 each. The
test split is scored once, so it draws twice the per-point sample. Every
evaluation point still scores the same seeded subset in the same order, so the
curve compares like with like.

| 500-step run | v0.4.0 | v0.4.1 |
|---|---|---|
| one evaluation point | 20 min | 2m41s |
| ten evaluation points | 3.3 h | 27 min |
| final test pass | 20 min | 5m30s |
| projected evaluation total | 3.75 h | 31 min |
| measured cost per example | 0.59 s | 0.63 s |

Training data is untouched: all 65,809 train records are still trained on, and
`training_summary.json` records `val` next to `val_total` and `test` next to
`test_total`, so a reported loss cannot be read as a full-split loss.

The eval callback is still the dominant cost of a run and still cannot be made
much faster. It is compute-bound, not launch-bound: the GPU reports 95-100%
utilization at 180 MHz of a 3090 MHz maximum. Batching the eval forwards was
re-measured on this host and rejected again, now at the 256-example sample:

| batch | s per example | speedup | peak VRAM |
|---|---|---|---|
| 1 | 1.092 | 1.00x | 6,541 MiB |
| 2 | 1.000 | 1.09x | 6,541 MiB |
| 4 | 0.974 | 1.12x | 7,053 MiB |
| 8 | out of memory | - | 8,151 MiB |

Batch 4 buys 12% for 512 MiB of headroom it does not have, and the loss is
unchanged (delta 1.2e-08, which is bf16 noise): right padding is exact here,
because a causal mask means a padded position cannot reach back into the valid
ones. Speed, not correctness, is why it stays off.

## An interrupted run continues by default

A 500-step run is over two hours on this card. Until now, losing the terminal
or a power cut cost the whole run, and a run interrupted at step 99 of a
500-step job left no checkpoint at all, because the first save lands at step
100. `make train` now continues from the last checkpoint: the adapter
weights, the optimizer moments, the position of the LR schedule, and the
dataloader and RNG cursor all come back, and the loss curve picks up where it
stopped. `--no-resume` opts out.

| | before | after |
|---|---|---|
| interrupted at step 99 | 42 min lost, nothing on disk | resumes from step 100 |
| files per checkpoint | 100 MB (weights only) | 145 MB (adds `optimizer.pt`) |
| checkpoints retained | 3 | 3 |
| eval points in the curve after a resume | from the resume on | all of them |

- `save_only_model` is off, so a checkpoint carries `optimizer.pt` and
  `scheduler.pt` next to the adapter. The weights alone are not a resumable
  state: `Trainer._load_optimizer_and_scheduler` silently skips them, and the
  run would continue on trained weights with a fresh optimizer and a rewound LR
  schedule. A checkpoint missing that state is reported and skipped rather than
  half-resumed.
- [`find_resume_checkpoint`](../../training/train_unsloth.py) takes
  the highest-numbered checkpoint in `--output-dir` and only when it is below
  the step budget, so a finished run does not turn the next `make all` into a
  no-op. Every rejection says why in the log.
- Each eval point is written to the trainer state's `log_history`, which every
  checkpoint carries. A resumed run therefore inherits the points the
  interrupted one scored, so early stopping keeps the same best and
  `eval_loss_history` in `training_summary.json` is whole. The summary records
  `experiment.resumed_from`; its `train_seconds` covers only the segment the
  process ran.

Measured by killing a run with SIGKILL one step after a checkpoint was written
and restarting it:

```text
Resuming from .../checkpoint-4 at step 4 of 6: the weights, optimizer, LR
  schedule, and data cursor continue where the previous run stopped, leaving
  2 step(s) to train.
Carried 2 earlier eval point(s) over from the checkpoint (best 2.4884)
eval curve: step 2 -> 2.5261, step 4 -> 2.4884, step 6 -> 2.3469
```

Raising `--max-steps` past a finished run's budget turns that run into a
resumable one, which is how a 250-step run continues to 500.

## What dedup was removing

The question behind this release was whether the dedup pass was also removing
the defect and natural-language variants it was supposed to preserve. It was
measured, per turn kind, by classifying every turn the build produces and every
turn it drops. The answer was "not for prose, yes for defects".

| kind | produced | kept | dropped verbatim | dropped by the cap |
|---|---:|---:|---:|---:|
| prose turns (doc QA, doc sections, toolchain QA) | 5,346 | 5,344 | 2 | 0 |
| defect turns | 36,772 | 21,598 | 6,882 | 8,292 |
| plain code turns | 50,442 | 26,666 | 8,817 | 14,959 |
| renamed code variants | 37,792 | 18,835 | 5,560 | 13,397 |
| reordered variants | 786 | 637 | 149 | 0 |

Prose was never at risk, and the reason is structural rather than lucky: a
prose turn carries no Ada fence, so it has no structural signature and the cap
cannot see it at all. Only a byte-identical record is ever dropped.

Defect turns were losing 22% of their number to the cap, for a reason in the
code rather than in the data. A defect turn's assistant reply is a diagnosis
followed by the *corrected* code, and that corrected code is the same code the
original record answers with, so both landed in one cap bucket. The bucket
filled with plain copies and single evaluations, and the cap then cut the
defect turns too. Across the 24,279 defect turns the parser drives (the 12,580
the pair pipeline adds are not attributable by family, because that work runs
in worker processes):

- 7,982 defect turns cut, 74 (family, code shape) combinations cut before the
  bucket was even full, and 1,291 code shapes lost at least one of the
  seventeen families outright;
- per-family survival was 29% (`old_misuse`), 33% (`contract`), 41%
  (`mismatch`), 46% (`syntax`).

So for a large part of the corpus the model was shown a code shape and never
shown what goes wrong in it. The defect is now part of the cap key
([`_ast_structural_signature`](../../data/processing_scripts/build_dataset.py)),
so the cap thins repeats of one diagnosis on one code shape and the seventeen
families no longer compete for the same slots:

| | before | after |
|---|---:|---:|
| defect turns kept | 9,802 | 12,728 |
| defect turns cut by the cap | 7,982 | 3,169 |
| (family, shape) combinations cut before the cap was full | 74 | 0 |
| `contract` / `mismatch` / `syntax` survival | 33% / 41% / 46% | 42% / 62% / 54% |
| total turns | 73,080 | 77,758 |
| train / val / test | 65,809 / 3,709 / 3,562 | 69,982 / 3,834 / 3,942 |

The cap value (10) is unchanged, and the experiment that chose it was run on
plain code records, which the keying does not touch. `make check-integrity`
passes on the rebuilt dataset.

## Keeping the sources current

The source cache is a tarball snapshot with no `.git`, so nothing noticed when
a repository moved. Each cache entry now records the commit of the default
branch it was fetched at, and three modes read that:

| command | network | effect |
|---|---|---|
| `make fetch-sources` | none | reuse the cache (what the pipeline calls) |
| `make check-sources` | one API call per repo | report cached vs upstream, exit 1 when anything moved |
| `make update-sources` | same, plus tarballs for the moved repos | re-fetch what moved, then rebuild the dataset |

A head that cannot be read (API quota, network) is reported as `unknown`, never
as "changed", so a failed check never re-fetches or destroys a good cache. An
entry fetched before commits were recorded shows as `untracked` and is
re-fetched once, with a warning, because that is the one case where a cache
that may be perfectly fine is touched. No separate rebuild step is needed: the
dataset stages fingerprint their input trees by content, so a refreshed
repository changes the digest and `make build-dataset` rebuilds by itself.

## `make clean` keeps the model

`make clean` removed `models/`, which held the 16 GB Qwen3-8B download that
`make check-model` skips when it is present, so a clean up meant a 16 GB
re-download before anything could run. It now removes the outputs, the generated
dataset, the stage stamps, the tokenized-split cache, and `training.log`, and
says that the model stays. `make clean-model` removes the model too.

## Epochs, packing, and the step budget

The usual training advice for a set this size is 2-3 epochs with sequence
packing and close validation tracking. Measured on this hardware:

- **Epochs.** One pass over 69,982 train records is 8,748 steps at 8 records
  per step, so the default `--max-steps 500` is 0.06 of an epoch. At the
  measured 13-21 s per step, an epoch is 30-48 h and 2-3 epochs is 60-140 h.
  The advice points at a real problem (the 500-step runs are under-trained:
  train loss was still falling at step 90) and at a job that is no longer
  awkward, because a run now resumes from its last checkpoint. The startup log
  states the epoch math rather than leaving it to be guessed from the step
  count.
- **Packing.** Not applicable, and not for want of trying. Its first reason is
  padding, and there is none: `per_device_train_batch_size` is 1, so no batch
  ever pads. Its second reason is throughput, and the forward is compute-bound
  (batching the eval 4-wide measured 1.12x for 7.05 GB of 8.15 GB; 8-wide
  OOMs), while a 4096-token window multiplies activation memory on a card that
  already peaks near 7.5 GB. Unsloth's packing also needs the Flash Attention
  varlen path, which this box does not have, so record boundaries could not be
  masked correctly.
- **Validation tracking.** Already there: an evaluation every 50 steps on the
  same seeded subset, now with a per-pass rate and ETA, the measured cost per
  example, the evaluation time still to come, and a trend verdict in the
  versioned report. The val split is in-distribution, so read it for the
  plateau and read the ada-eval BUILD/TEST/PROVE tallies for the model.

## Tests

- The budget case in
  [`tests/test_train_data.py`](../../tests/test_train_data.py) now reads the
  shipped `--eval-sample` and `--test-sample` defaults instead of repeating
  2,000 in the test, so raising them trips the test instead of the log.
- A new case pins what caused the stall: one default evaluation point must
  project to under 10 minutes.
- Nine cases pin the resume decision: no output directory, no checkpoint, the
  highest-numbered checkpoint wins, a checkpoint at or past the budget is
  ignored, one missing the optimizer state is rejected, and an unreadable or
  step-zero trainer state is rejected. One more asserts that the config keeps
  `save_only_model` off, so a future edit cannot quietly make every checkpoint
  unresumable. 51 cases in the file, all passing.
- Three cases pin the new cap keying in
  [`tests/test_defect_families.py`](../../tests/test_defect_families.py):
  two defect families on one code shape each get a budget, a defect turn does
  not collide with the record it corrects, and a non-defect turn still keys on
  code alone.
- Two cases in `tests/test_stage_state.py` cover what a moved upstream commit
  does to the dataset stages: a changed source file rebuilds, and re-recording
  the same content under a new fetch timestamp does not. 360 tests pass.
