# Changelog v0.4.1

Not the whole log: see the [changelog index](index.md) for every version and
the [results index](../results/README.md) for the measured numbers.

No evaluation run was made for this version, so there is no
`result-v0.4.1.md`; nothing here quotes benchmark numbers. What this version
changes is what `make train` prints while it evaluates, how many examples
each evaluation point scores, and what a run does when it dies half way.

**Read this before comparing losses across versions.** The per-step
`eval_loss` is now measured on a seeded 256-example subset of the val split
and the reported test loss on a 512-example subset, where
[v0.4.0](v0.4.0.md) used 2,000 examples of each. They are comparable
run-to-run within this version, and not to the 2,000-example figures in
v0.4.0 or the full-split figures in [v0.3.0](v0.3.0.md). The generation
metrics (build, test, prove, BLEU, compliance) are unaffected: nothing in the
evaluation path changed.

## An evaluation pass no longer looks like a hang

A run reached an evaluation point and printed nothing until the pass
finished. With the v0.4.0 sample size that was 20 minutes of silence between
progress-bar lines, and the only symptom was a bar that had stopped moving at
99/500. The pass now logs as it goes, using the same counter the dataset
stages use ([`Progress`](../../data/processing_scripts/progress.py)), and the
eval-loss line projects the evaluation time still to come from the cost that
pass measured.

A real pass, from `make train` at step 2:

```text
[val eval] starting (256 items)
[val eval] 30/256 (12%) 1.0 items/s, elapsed 31s, eta 3m57s
[val eval] 117/256 (46%) 1.3 items/s, elapsed 1m32s, eta 1m49s
[val eval] 256/256 (100%) 1.6 items/s, elapsed 2m41s, eta 0s
val pass: 256 examples, 143580 tokens, 0.63 s per example
eval_loss at step 2: 2.5663 (best 2.5663); 0.63 s per example, ~0 min of
  evaluation still to come (0 more point(s), then the test pass)
```

## The sample defaults

`--eval-sample` is 256 and `--test-sample` is 512, down from 2,000 each. The
test split is scored once, so it draws twice the per-point sample. Every
evaluation point still scores the same seeded subset in the same order, so the
curve compares like with like.

| 500-step run | v0.4.0 | v0.4.1 |
|---|---|---|
| one evaluation point | 20 min | 2m41s |
| ten evaluation points | 3.3 h | 27 min |
| final test pass | 20 min | 5m30s |
| projected evaluation total | 3.75 h | 31 min |
| measured cost per example | 0.59 s | 0.63 s |

Training data is untouched: all 65,809 train records are still trained on, and
`training_summary.json` records `val` next to `val_total` and `test` next to
`test_total`, so a reported loss cannot be read as a full-split loss.

The eval callback is still the dominant cost of a run and still cannot be made
much faster. It is compute-bound, not launch-bound: the GPU reports 95-100%
utilization at 180 MHz of a 3090 MHz maximum. Batching the eval forwards was
re-measured on this host and rejected again, now at the 256-example sample:

| batch | s per example | speedup | peak VRAM |
|---|---|---|---|
| 1 | 1.092 | 1.00x | 6,541 MiB |
| 2 | 1.000 | 1.09x | 6,541 MiB |
| 4 | 0.974 | 1.12x | 7,053 MiB |
| 8 | out of memory | - | 8,151 MiB |

Batch 4 buys 12% for 512 MiB of headroom it does not have, and the loss is
unchanged (delta 1.2e-08, which is bf16 noise): right padding is exact here,
because a causal mask means a padded position cannot reach back into the valid
ones. Speed, not correctness, is why it stays off.

## An interrupted run continues by default

A 500-step run is over two hours on this card. Until now, losing the terminal
or a power cut cost the whole run, and a run interrupted at step 99 of a
500-step job left no checkpoint at all, because the first save lands at step
100. `make train` now continues from the last checkpoint: the adapter
weights, the optimizer moments, the position of the LR schedule, and the
dataloader and RNG cursor all come back, and the loss curve picks up where it
stopped. `--no-resume` opts out.

| | before | after |
|---|---|---|
| interrupted at step 99 | 42 min lost, nothing on disk | resumes from step 100 |
| files per checkpoint | 100 MB (weights only) | 145 MB (adds `optimizer.pt`) |
| checkpoints retained | 3 | 3 |
| eval points in the curve after a resume | from the resume on | all of them |

- `save_only_model` is off, so a checkpoint carries `optimizer.pt` and
  `scheduler.pt` next to the adapter. The weights alone are not a resumable
  state: `Trainer._load_optimizer_and_scheduler` silently skips them, and the
  run would continue on trained weights with a fresh optimizer and a rewound LR
  schedule. A checkpoint missing that state is reported and skipped rather than
  half-resumed.
- [`find_resume_checkpoint`](../../training/train_unsloth.py) takes
  the highest-numbered checkpoint in `--output-dir` and only when it is below
  the step budget, so a finished run does not turn the next `make all` into a
  no-op. Every rejection says why in the log.
- Each eval point is written to the trainer state's `log_history`, which every
  checkpoint carries. A resumed run therefore inherits the points the
  interrupted one scored, so early stopping keeps the same best and
  `eval_loss_history` in `training_summary.json` is whole. The summary records
  `experiment.resumed_from`; its `train_seconds` covers only the segment the
  process ran.

Measured by killing a run with SIGKILL one step after a checkpoint was written
and restarting it:

```text
Resuming from .../checkpoint-4 at step 4 of 6: the weights, optimizer, LR
  schedule, and data cursor continue where the previous run stopped, leaving
  2 step(s) to train.
Carried 2 earlier eval point(s) over from the checkpoint (best 2.4884)
eval curve: step 2 -> 2.5261, step 4 -> 2.4884, step 6 -> 2.3469
```

Raising `--max-steps` past a finished run's budget turns that run into a
resumable one, which is how a 250-step run continues to 500.

## Tests

- The budget case in
  [`tests/test_train_data.py`](../../tests/test_train_data.py) now reads the
  shipped `--eval-sample` and `--test-sample` defaults instead of repeating
  2,000 in the test, so raising them trips the test instead of the log.
- A new case pins what caused the stall: one default evaluation point must
  project to under 10 minutes.
- Nine cases pin the resume decision: no output directory, no checkpoint, the
  highest-numbered checkpoint wins, a checkpoint at or past the budget is
  ignored, one missing the optimizer state is rejected, and an unreadable or
  step-zero trainer state is rejected. One more asserts that the config keeps
  `save_only_model` off, so a future edit cannot quietly make every checkpoint
  unresumable. 51 cases in the file, all passing.
