# Changelog v0.8.0

Not the whole log: see the [changelog index](index.md) for every version and
the [results index](../results/README.md) for the measured numbers.

This version is the harness and extraction work that
the v0.7.0 measurement demanded, plus the scope for the extraction track
that follows. The scope is [`plan.md`](../../plan.md); it is the larger half
of this version's intent and is deliberately not built here.

The evaluation run for this version is
[`result-v0.8.0.md`](../results/result-v0.8.0.md), on an adapter retrained on
the 80,718-turn dataset, and
[`docs/eval-analysis-v0.8.0.md`](../eval-analysis-v0.8.0.md) decomposes it.
**The training set changed**, from 80,262 to 80,718 turns, and the delta comes
from two extraction bug fixes rather than a new turn kind: the ada-spark
guidance globs now match the repository's real layout (5 of 6 documents load,
against 2 before) and `pair_files` keys a body on `(directory, stem)`, which
fixes the 138 turns that paired a specification with a foreign body. The
kinds the v0.6.0 and v0.7.0 entries introduced are unchanged
(`contract_synth` 708, `spark_verified` 568, `lab_pair` 252, `assurance_qa`
5). Runs on the two datasets are not comparable for loss.

One measurement below is *not* a v0.8.0 model result, and is kept as the
evidence that the harness fix is the fix: the v0.7.0 adapter re-scored with
the fixed harness.

## The regression: a package body written into a package spec

Every ada-eval sample targets a spec (`.ads`) file, and the fine-tune often
replies with the unit's *body*. The harness had one fallback for a reply
without `File:` headers: write the fenced block at the target path. So the
block landed in the spec, and the project became

```ada
package body Integer_Utils is
   ...
end Integer_Utils;
```

inside a package spec, which GNAT rejects. The sample failed BUILD for a
routing mistake, not for wrong Ada. On the v0.7.0 run six of nineteen
fine-tuned replies did this and all six failed; the base model emitted the
requested `File: <path>` format on all nineteen and never triggered it.

`eval/generate.py` now routes a body-only fallback block to the sibling
`.adb` (`body_sibling`, `opens_with_package_body`), and only when the base
tree already carries that mirror file, so the repair never invents a file the
project did not have. An unknown tree gets no repair at all, and an explicit
`File:` entry still wins: when the model names the file, its choice is
authoritative. Comment lines before the clause are skipped, because a gnatdoc
preamble is the normal shape here, but a reply carrying a whole project opens
with its spec and is therefore not rerouted.

## A harness repair must not be able to flatter the model

So the reply shape is now recorded per sample and printed next to the
scores. `eval/generate.py` writes
`outputs/generated_solutions/<label>/generation_meta.json`; `make eval`
reports it as `Reply format: fenced_block=15, file_blocks=4 (untouched
13/19)`.

Both numbers matter. `file_blocks` is the format the prompt asks for, and a
model that only ever uses the fallback cannot change a project with more than
one source file. `untouched` is the sharper one: a reply that only echoes the
base file leaves the base project in place, so the sample is then scored on
the base tree's build and test result. Thirteen of nineteen fine-tuned samples
are in that state, against two of nineteen for the base model, and any build
number has to be read with that in mind.

### What the fix does to the numbers

Same adapter (the v0.7.0 one), same benchmark, harness repaired:

| | v0.7.0 run | v0.7.0 adapter, fixed harness |
|---|---|---|
| Fine-tuned build | 10/19 (52.6%) | 16/19 (84.2%) |
| Fine-tuned test | 8/19 (42.1%) | 11/19 (57.9%) |
| Prove errors | 9 | 3 |
| Base build / test | 7 / 5 | 7 / 5 |

The base model is unmoved, and the fine-tuned numbers return exactly to the
v0.4.1 level, which is what the six broken samples cost. The recovery is not
the model writing better Ada: it is six projects no longer being broken by
the harness. `docs/results/result-v0.7.0.md` is left as it was measured; it
is the record of that dataset with that harness, not a number to update.

## Two pipeline gaps that produced wrong numbers quietly

**`make eval` scored against a hollow benchmark.** ada-eval's
`data/base/compacted/*.jsonl` is derived from `expanded` and is not version
controlled, so a re-fetched cache has none and `make eval` exited 1. Worse,
ada-eval's packer is git-aware: `get_contents_git_aware` runs `git ls-files`
when the path is inside a worktree, and this repository is one while
`data/raw_repos/` is gitignored, so the pack *succeeded* while writing
records with an empty `canonical_solution`. `make eval` then reported
BLEU 0.0 with every standard `Unknown` and 19 samples "scored", which reads
as a model result and is not one.

`scripts/pack_eval_data.py` (new, `make eval-data`, a prerequisite of
`make eval`) packs with `GIT_CEILING_DIRECTORIES` set to the checkout so
git's upward search stops there, passes `force=True` because the same
git-awareness makes ada-eval's own uncommitted-changes guard fire, and then
**verifies** that every packed record carries solution files.
`load_reference_index` drops hollow records and logs an error naming them.

**`make all` reported the previous run's tallies.** `baseline_eval` prints
BUILD/TEST/PROVE but reads them from `outputs/eval_results/`, which only
`eval_pipeline.py` writes, and `all` ran `eval` first. The summary therefore
showed the previous run's numbers, and on a clean tree `print_stats_block`
printed nothing at all, which reads as "nothing failed". The order is now
`generate eval-pipeline eval eval-report`, the stats block prints
`no results (run make eval-pipeline first)` instead of nothing, and
`tests/test_makefile.py` fails if the order changes again.

## Two extraction bugs, both found by looking at what the pipeline read

**ada-spark guidance was silently dropped.** `_SKILL_DOC_PATTERNS` matched
the ada-spark repository root (`SKILL.md`, `agent-knowledge/*.md`) while the
repo keeps its agent skill under `skills/ada-spark/`, the layout the other
two repos already used. Two documents were loaded and seven missed,
including `references/spark-proof.md` and `references/toolchain.md`, which is
where the proof guidance actually lives. The globs now match the real layout:
six files are discovered and five load (the loader's 16,000-char per-source
budget excludes the last), against two before. The proof workflow text from
`spark-proof.md` now reaches 824 training records.

**138 `code_pair` turns paired a spec with an unrelated body.** `pair_files`
indexed bodies by stem alone across every input tree, so
`sorting/sort.ads` could pair with `search/sort.adb` and the turn would
present a spec and a foreign body as one unit. Measured on Ada-Algorithms:
120 cross-directory pairs, 18 more in TLALOC, 1 in Ada_CRDT. The index key is
now `(directory, stem)`. The same function's `extract_package_name` had a
related bug: its regex required the word "package" twice, so
`package body Foo is` never matched and every body file fell back to the
filename stem.

**Correct pairing exposed a false defect claim, and
`make validate-defects` had been clean only because of the mispairing.**
`validate_defects.py` draws its pairs through the same `pair_files`, so the
fix fed it correctly paired projects it had never seen. Two pairs then failed:
both the ada-eval `search_array` sample, whose spec declares a record
component `Content : Integer` and whose body assigns it in aggregate position
(`Result := (Found => True, Content => I)`). The `typo` and `scoping`
families both claim `error: "X" is undefined`, but in aggregate position GNAT
resolves the aggregate against the subtype and reports
`"Cnotent" is not a component of the aggregate subtype`. Under the old
pairing the spec never met the body that used its component, so the shape was
never compiled.

Both families now decline a declaration whose first use is in aggregate
position (`_is_aggregate_component_use`), the same way `typo` already declined
a use site on a subprogram profile line. On this pair they decline entirely,
which is the honest outcome: no candidate, no claim. `make validate-defects`
is clean again, with `typo` 10/10 and `scoping` 11/11 where both previously
skipped or mismatched on these units.

| File | Before | After |
|---|---|---|
| `tests/test_eval_pipeline.py` | 0 | 37 |
| `tests/test_pack_eval_data.py` | 0 | 15 |
| `tests/test_makefile.py` | 0 | 16 |

| `tests/test_build_dataset.py` | 62 | 81 |
| `tests/test_defect_families.py` | 41 | 48 |

`eval/eval_pipeline.py` had no tests at all and decides the per-dataset output
path every other scoring module reads, so it was the largest hole.
`tests/test_makefile.py` is new because `make all`'s ordering was unguarded
and had already produced one wrong published run; it also found that
`gen-verified-spark` was missing from `make help`.

`make lint` now type-checks `eval/generate.py` and `eval/eval_pipeline.py`,
the only Python in the repo mypy did not see, and `MYPYPATH` gained
`scripts` so `alire_env` resolves. Two test failures were real findings while
writing them: a leading gnatdoc comment blocked the routing repair, and the
sidecar's `routed_body` field could never fire because it tested the wrong
condition.

## Scoped, not built

[`plan.md`](../../plan.md) carries the measured inventory of what no
extractor reads, ordered by value: write-shaped turns for the evaluation
prompt (94 of 72,464 train turns have its shape), unit-test turns from the
1,858 test harnesses already in the cache (nothing trains the dimension the
benchmark scores), the Ada 83 conformance suite as error-diagnosis turns
(4,142 files, 12,091 inline `-- ERROR:` markers), ~11,000 unparsed
documentation sections, AdaDoc contract-documentation turns, `.gpr`
build-configuration turns, and the `training_material` Ada that no builder
reaches.

Every volume in that inventory was counted in the cache. None of it is built
here, and none of it may ship without `make check-integrity`,
`make validate-defects` and a result file to compare against v0.4.1.

## The measured result

| Metric | v0.4.1 | v0.7.0 | v0.8.0 |
|---|---|---|---|
| Fine-tuned build | 16/19 (84.2%) | 10/19 (52.6%) | 15/19 (78.9%) |
| Fine-tuned test | 11/19 (57.9%) | 8/19 (42.1%) | 10/19 (52.6%) |
| Proved | 0 | 0 | 1 |
| Prove errors | 3 | 9 | 2 |
| BLEU-4 | 0.8141 | 0.5617 | 0.7093 |
| Exact match | 8/19 | 4/19 | 6/19 |
| Standard compliance | 0.2807 | 0.3333 | 0.2456 |
| Reply format | not recorded | 4/19 | 19/19 `file_blocks` |
| Replies that changed nothing | not recorded | not recorded | 13/19 |
| Test loss | 0.2242 | 0.2024 | 0.2118 |

The regression is over. Build and test are back at the v0.4.1 level, no
sample fails BUILD because a package body was written into a package spec,
prove errors are the lowest of any run, and one sample is proved: `HumanEval_2_truncate_number`, the only sample
whose base tree has no body at all. The model wrote the body into
`src/placeholder.adb`, kept the given contracts, and gnatprove discharged 6 of
6 checks with no `pragma Assume`. At 500 steps that is the most informative
number in the run.

The other half of the run is a warning, and the harness change above is what
made it visible. Thirteen of nineteen replies changed nothing, and 18 of the 19
ada-eval base trees already contain a body for the target subprogram, so an
echo keeps a compiling project:

| Group | Samples | Build | Test | Proved |
|---|---|---|---|---|
| Changed nothing | 13 | 12 | 8 | 0 |
| Edited | 6 | 3 | 2 | 1 |

Fifteen builds is twelve inherited and three earned, and on the samples it
edits the fine-tune is no better than the base model. The similarity metrics
recovered for the same reason and are not evidence of writing better Ada: all
6 exact matches are echoes, and BLEU-4 scores the target file only, which is
identical between base and canonical for 6 samples. The reference metrics went
the other way: compliance fell to 0.2456 because the base files carry Ada 83
constructs the check counts as non-compliant and the model now reproduces
them.

Two samples also failed BUILD for a harness reason, and that is not fixed
here. On `char_count_1` and `char_count_2` the model replied with a single
`File: main.gpr` entry; `parse_generated_files` drops entries outside the
target directory and then writes the fenced block at the target path, so the
project file's text landed in `src/string_utils.ads`. It is the mirror image of
the routing bug this version fixed, it costs 2 builds and 2 tests, and
[`plan.md`](../../plan.md) carries the rule that stops it.

## For the next run

The bar is the split, not the total. A run that reaches 16/19 build by leaving
the base project in place is not the win v0.4.1's 16/19 was, so v0.9.0 reports
build, test and prove on the samples the model changed beside the samples it
echoed, and every extraction item in [`plan.md`](../../plan.md) is judged
against the edited-sample counts.
